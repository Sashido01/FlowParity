# Публикация и проверка выпуска

FlowParity опубликован в `Sashido01/FlowParity`. Публичный репозиторий начинался с коммита только с README; локальная история должна сохранять этот коммит предком. Не используйте force push и не публикуйте локальные исследования, учётные данные, снимки экрана, приватные заметки или Git bundle.

## Перед публикацией

1. Проверьте подготовленные к коммиту файлы и историю. Убедитесь, что текущий `origin/main` является основой, а рабочее дерево содержит только предназначенные для публикации файлы.
2. Запустите документированные тесты, компиляцию, проверки CLI, ссылок и `git diff --check`. Записывайте фактические результаты; поведение Windows/Codex и hosted CI считается непроверенным, пока оно не наблюдалось.
3. Проверьте все публикуемые коммиты на секреты и приватные материалы. Синтетический пример должен оставаться явно обозначенным.
4. Выполняйте обычный `git push origin main`; расхождение разрешайте штатными операциями Git с проверкой итоговой истории. Не применяйте force push.
5. Откройте запуски Actions для финального коммита и проверьте каждую настроенную ОС и версию Python. Файл workflow или ожидающий запуск не являются успешным результатом.
6. Проверьте публичное дерево, отображение README, относительные ссылки, описание/topics репозитория и доступные настройки безопасности.

## Версия и выпуск

Поддерживайте одинаковую версию в `VERSION`, обоих README и обоих changelog. Для совместимого первого проверенного выпуска используйте увеличение patch-версии. Создавайте GitHub Release только после проверки точного содержимого тега и доказательств приёмки; локальные тесты сами по себе не подтверждают стабильность или соответствие приложения.

## Границы текущих проверок

CLI оценивает ссылки на доказательства и аттестации, записанные автором. Он не открывает файлы доказательств, не запускает целевое приложение, не активирует навыки Codex и не устанавливает юридические права независимо. Недоступные проверки Windows, hosted CI или Codex отмечайте `NOT_VERIFIED`.
